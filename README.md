# Прототип поиска контекстно зависимых review-комментариев

Если предыдущая версия уже адаптирована к корпоративному GitLab и агенту Nessy на основе Qwen Code, начать с [задания для рабочего GLM по слиянию обновления](UPGRADE_FOR_NESSY.md): delta файлов, сохранение готовых адаптеров, runtime boundary и acceptance checks.

Цель, уточнённая 27 октября 2026 года, — находить контекстно зависимые комментарии. Сначала получаем оценку L только по комментарию и снипету, затем независимую оценку R через free planning по репозиторию. Если человеческая оценка H совпадает с R и расходится с L, пример становится кандидатом на ambiguity; следующий целевой проход проверяет, действительно ли причиной является недостающий контекст. Основной протокол — [15-context-dependence.md](docs/15-context-dependence.md).

В рабочем сервисе уже существуют генератор по аспектам, severity/complexity- и reaction/acceptance-классификаторы, метаранкер и post-processing фактических реакций. Они остаются рабочим контуром. Новый `ambiguity-run` реализует отбор H=R≠L, независимую проверку контекстной причины, повтор L и контроль L с выбранным решающим контекстом. [Инструкция запуска](docs/16-ambiguity-runbook.md), [результаты pilot](docs/18-ambiguity-pilot.md) и [независимый human-аудит](docs/17-ambiguity-human-audit.md).

В L/R используется отдельная шкала `comment-endorsement-v1`: поддержать замечание / отвергнуть / недостаточно данных. Человеческие реакции допускаются только через явный `--reaction-proxy`, с сохранением их слабой природы; ручные endorsement annotations передаются отдельным файлом. Ни candidate, ни подтверждение моделью не становятся human ground truth. Будущий ambiguity-классификатор ещё не обучался.

Реализован прототип на Pi SDK 1.3.0 и локальной `qwen3.8-flash-next-mirai-s`: сбор GitHub inline review comments, исторические snapshots, три режима контекста, очередь с возобновлением, traces, проверка JSON и evidence. В исходном smoke общего judge выполнены 120 оценок на 40 комментариях и ещё 4 оценки двух примеров с дизлайками. [Итоговые результаты](docs/13-prototype-results.md): все validators прошли у local 39/40, static 36/40 и agent 18/40. Это техническая пригодность outputs, не accuracy; для массовой автоматической разметки agent пока недостаточно устойчив. Рабочие данные в проект не переносились.

Последующее [укрепление прототипа](docs/14-hardening.md) добавляет нумерованный контекст, исторические metadata, восстановление прерванной очереди, парное сравнение прогонов и отдельный контракт ссылок на целые chunks. На одинаковой целенаправленно выбранной regression-выборке из 16 комментариев число валидных outputs выросло с 4 до 15; это не оценка factual accuracy. Основной response contract — compact-0.3.0, старые runs сохранены.

Агент выдаёт компактные judgments и ссылки на показанный код; harness подставляет точные цитаты и служебные идентификаторы. Исходный ответ модели сохраняется отдельно от canonical assessment. Примеры работы и ограничения проверки приведены в [walkthrough](docs/09-walkthrough.md) и [разборе первых десяти случаев основного smoke](docs/10-smoke-cases.md).

Начать с [инструкции запуска](docs/06-runbook.md). [Пакет переноса](docs/07-handoff.md) описывает замену GitHub/Pi/endpoint, а [ручной аудит](docs/08-human-audit.md) — что ещё требуется для выводов о качестве. LoRA не обучались. Оценка LLM не считается человеческой разметкой.

После клонирования скопировать `configs/default.example.json` в `configs/default.json` и настроить URL и ID модели. Ключ задаётся через `MB_JUDGE_API_KEY`. Рабочий `default.json`, captures и результаты прогонов исключены из Git; в репозитории хранится только шаблон подключения.

Основное правило: реакция пользователя, заключение LLM и проверенный человеком факт — три разных источника. Несогласие между ними само по себе не разрешает исправлять исходную реакцию.

[Проверка реальных реакций](docs/11-reaction-probe.md) хранится отдельно: 6 комментариев Sourcery, 2 человеческих лайка и 12 собственных реакций бота. Она проверяет фильтрацию сигналов; оценка естественного label noise пока невозможна.

В [дополнительной выборке Nuitka](docs/12-reaction-followup.md) ещё 7 комментариев: 2 человеческих дизлайка и 1 лайк. На двух отрицательных примерах выполнен отдельный local/agent demo, все 4 ответа прошли validators, но в одном объяснении teacher обнаружена фактическая ошибка. Выборка отобрана целенаправленно и не является оценкой распространённости шума.

Быстрая проверка нового сценария после установки зависимостей и настройки модели:

```powershell
.\.venv\Scripts\python.exe scripts/make_ambiguity_controls.py
.\aicr.ps1 --data data/ambiguity-controls-v1 ambiguity-run --name controls --limit 4 --human data/ambiguity-controls-v1/human/synthetic-references.jsonl --synthetic-demo
```

Это четыре синтетических controls, без реальных human labels. Для рабочих/публичных samples использовать [новый runbook](docs/16-ambiguity-runbook.md); для переноса адаптеров — [handoff](docs/07-handoff.md).

Первый прототип включает GitHub collector, фиксацию исторического кода, local/static/agent проходы через локальную модель, trace, проверку evidence и evaluator для будущей независимой ручной оценки. Команда `triage` формирует post-hoc список расхождений и недостающего контекста для аудита реакций; исходные labels не исправляет. Обучение новых LoRA и production ranking policy — последующие этапы после проверки данных и качества teacher.

Портирование на работу должно заменять три адаптера: GitHub → GitLab, PiRunner → NessyRunner, локальный model endpoint → рабочий endpoint. Taxonomy, протокол эксперимента и формат результатов остаются общими.

Рабочие параметры подтверждены пользователем: severity `nit / minor / serious / critical`, complexity `1–5`, обе головы ordinal; вход реранкера — `comment + code snippet + short generator rationale`. Контракт использует эти значения и сохраняет rationale отдельно. Точный смысл complexity и границы классов требуют исходной judge-рубрики; временные описания уровней не считаются восстановленной рабочей инструкцией.
