# Как прототип различает ошибку и нехватку контекста

Ниже — инженерный пример с искусственным кодом. Он не входит в публичный корпус и не является human reference или измерением качества модели.

Комментарий: «`reciprocal(0)` вызовет деление на ноль; добавьте проверку».

Начальный snippet:

```python
from guards import denominator

def reciprocal(x):
    return 1 / denominator(x)
```

Local assessment `synthetic-2026-10-21T200137456803Z`: **unverifiable**, контекста недостаточно, действие `request_context`. Причина — неизвестна реализация `denominator(0)`. Это корректная постановка неопределённости: отсутствие реализации не доказывает ни ошибку, ни безопасность.

В agent режиме Pi нашёл и прочитал `guards.py`:

```python
def denominator(x):
    """Return a non-zero integer divisor, including when x is zero."""
    return max(1, abs(int(x)))
```

Agent assessment: **refuted**, контекст достаточен, действие `discard`. Для конкретного входа `0` знаменатель равен `1`. В финале сохранены anchors на оба файла; validator проверил, что фрагменты действительно показаны модели и цитаты совпадают с snapshot.

Если бы рядом с этим комментарием стоял dislike, результат всё равно не доказывал бы мотив пользователя. Возможные причины реакции и factual verdict сохраняются отдельно. Если бы стоял like, прототип тоже не должен автоматически менять его на dislike.

Первый запуск этого же примера был отклонён из-за неправильной связи claim ↔ evidence. После уточнения контракта повторный запуск прошёл. Это демонстрирует назначение валидации, но не позволяет считать модельную разметку достоверной без независимой проверки.

Реальные оценки экспортируются в `runs/<run-id>/cases.jsonl`: там явно указано `model_generated_not_human_verified`. Для оценки того, когда контекст помог или навредил, нужны repository-stage human annotations по инструкции в docs/08-human-audit.md.

## Реальный пример: ширина ряда CTA

Sample `gh-5d2580b096f440eb0400d520`, run `smoke-frozen-a948d5ff5fb9`, snapshot `snap-ebc29ec5e5aad7949c86622f`.

Замечание бота: при viewport 384–407px ряд кнопок и иконок шириной 360px не помещается между отступами hero; нужно изменить breakpoint переноса с 383px на 407px или разрешить перенос по доступной ширине.

| Режим | Verdict модели | Контекст и результат |
| --- | --- | --- |
| local | partially_supported | Видит правило max-width 383px, но не размеры кнопок, иконок и отступов |
| static | partially_supported | Расширенное окно не содержит всех определяющих CSS-правил и HTML |
| agent | supported | Нашёл mobile width 4.5rem для трёх кнопок, width 3rem для трёх иконок, отступы 1.5rem с двух сторон и overflow:hidden |

Расчёт модели: `3×4.5rem + 3×3rem = 22.5rem`; при 16px/rem это 360px, а два отступа дают ещё 48px. Модель сослалась на `styles.css:257`, `styles.css:296`, `styles.css:345`, `styles.css:382`, `styles.css:732`, `styles.css:736`, `styles.css:809` и `index.html:59`. Чтение исторических файлов подтверждает наличие перечисленных правил; браузерная проверка геометрии не выполнялась. Семантическая полнота anchors и предпосылки о root font-size требуют отдельной проверки.

Agent сделал 7 запросов и 12 tool calls за 106.141s; все три результата прошли JSON, межполевой и evidence validator. Это наблюдаемый переход verdict после контекста, не измеренное улучшение качества. Body этого комментария редактировался, поэтому sample current_only и не входит в strict cohort. Данные иллюстративные, не ground truth для обучения.
